**1. Rehearsal Of Halo - 2D 액션 멀티플레이 보스러시 프로젝트**

* Unity Engine으로 개발한 2D 액션 멀티플레이 보스러시 프로젝트입니다. 팀장 및 메인 기획을 담당했으며, 플레이어 시스템, 스킬 시스템, 샤드 시스템, 네트워크 프로그래밍을 주로 구현했습니다.

* 플레이어의 평타와 스킬을 분리하고, 무기 / 스킬 / 샤드가 런타임에 조합되는 구조를 설계했습니다. 이를 통해 장착한 무기와 샤드 구성에 따라 스킬의 데미지, 범위, 효과가 달라지도록 구현했습니다.

* 멀티플레이 환경에서는 서버 권위 구조를 기준으로 플레이어 스폰, 스킬 생성, 데미지 판정, 주요 게임 이벤트를 서버에서 처리하도록 구성했습니다. 클라이언트는 입력 전달과 이펙트 재생을 중심으로 동작하도록 역할을 분리했습니다.

**4. 핵심 기술 구현 사항**

* **4-1. 평타와 스킬의 책임 분리**

  평타와 스킬을 하나의 공격 로직으로 묶지 않고, 서로 다른 처리 흐름으로 분리했습니다.

  평타는 플레이어 애니메이션 이벤트에 맞춰 타격 판정이 발생하도록 구현했습니다. 이를 통해 근접 공격의 타이밍과 애니메이션 싱크를 맞출 수 있도록 했습니다.

  반면 스킬은 독립적인 네트워크 투사체로 생성되도록 구성했습니다. 스킬 생성, 이동, 충돌, 데미지 판정은 네트워크 환경에서 동기화될 수 있도록 분리하여 처리했습니다.

* **4-2. 무기 → 스킬 → 샤드 런타임 컴포지션 설계**

  무기, 스킬, 샤드가 런타임에 결합하여 최종 공격 성능을 결정하는 구조를 설계했습니다.

  플레이어가 장착한 무기는 사용할 수 있는 스킬의 기반이 되고, 스킬은 실제 공격 방식과 판정 범위를 담당합니다. 샤드는 스킬에 추가 효과를 부여하여 데미지, 범위, 속성, 부가 효과 등을 변경할 수 있도록 구성했습니다.

  이를 통해 새로운 무기나 샤드를 추가할 때 기존 플레이어 공격 로직을 크게 수정하지 않고 확장할 수 있도록 설계했습니다.

* **4-3. 서버 권위 기반 네트워크 구조**

  멀티플레이 환경에서 핵심 게임 로직은 서버가 최종 권한을 갖도록 구성했습니다.

  플레이어 이동, 데미지 판정, 스킬 생성, 주요 전역 이벤트 처리는 서버에서 검증하고 실행하도록 설계했습니다. 클라이언트는 입력을 서버로 전달하고, 서버에서 확정된 결과를 기반으로 이펙트와 UI를 재생하는 방식으로 역할을 분리했습니다.

  이를 통해 클라이언트 간 상태 불일치를 줄이고, 스킬과 데미지 판정이 각 클라이언트에서 다르게 계산되는 문제를 방지하고자 했습니다.

* **4-4. RPC 기반 스킬 생성 및 동기화**

  스킬 사용 요청은 클라이언트 입력에서 시작되지만, 실제 스킬 오브젝트 생성은 서버에서 처리하도록 구성했습니다.

  클라이언트가 스킬 사용 입력을 보내면 서버가 사용 가능 여부를 확인하고, NetworkObject를 생성한 뒤 클라이언트들에게 동기화합니다. 이를 통해 각 클라이언트가 임의로 스킬을 생성하지 않도록 하고, 동일한 스킬 상태를 공유할 수 있도록 했습니다.

**5. 트러블 슈팅 히스토리**

1. **NetworkManager와 수동 스폰 시스템 충돌로 인한 중복 스폰 이슈**

* 문제 상황 : 멀티플레이 룸 진입 및 인게임 씬 전환 시, 각 클라이언트마다 플레이어 캐릭터가 2개씩 생성되는 문제가 발생했습니다.

* 원인 분석 : Unity Netcode for GameObjects의 NetworkManager에 등록된 Player Prefab 자동 스폰 기능과, 직접 구현한 NetworkTransmission의 수동 스폰 로직이 동시에 실행되고 있었습니다. 그 결과 NetworkManager가 한 번, NetworkTransmission이 한 번 플레이어를 생성하면서 중복 스폰이 발생했습니다.

* 해결 방안 : NetworkManager의 Player Prefab 등록을 해제하여 자동 스폰을 차단했습니다. 이후 NetworkTransmission에서만 클라이언트 ID와 세션 상태를 확인한 뒤, 서버 권한으로 SpawnAsPlayerObject()를 호출하도록 스폰 흐름을 일원화했습니다.

* 배운 점 : 네트워크 오브젝트 생성은 자동 스폰과 수동 스폰이 동시에 섞이면 추적이 어려워집니다. 따라서 플레이어 생성 흐름은 한 곳에서만 관리해야 하며, 서버 권한으로 명확하게 제어하는 구조가 중요하다는 점을 배웠습니다.

2. **멀티플레이 환경에서 원격 플레이어 이동 지터링 이슈**

* 문제 상황 : 로컬 클라이언트에서는 플레이어 이동이 자연스럽게 보였지만, 원격 클라이언트 시점에서 다른 플레이어의 이동이 끊겨 보이거나 순간적으로 위치가 튀는 문제가 발생했습니다.

* 원인 분석 : 원격 플레이어의 위치가 물리 갱신 주기와 네트워크 패킷 수신 주기의 차이에 따라 갱신되면서, 프레임 사이의 위치 변화가 부드럽게 보간되지 않았습니다. 또한 Rigidbody2D의 보간 옵션이 꺼져 있어, 패킷 사이의 공백 프레임에서 이동이 끊겨 보이는 문제가 있었습니다.

* 해결 방안 : 원격 플레이어 프리팹의 Rigidbody2D 보간 옵션을 Interpolate로 변경했습니다. 이를 통해 이전 물리 위치와 현재 물리 위치 사이를 보간하여, 원격 클라이언트에서 보이는 이동이 더 부드럽게 출력되도록 수정했습니다.

* 배운 점 : 멀티플레이 이동 동기화에서는 서버 권위 구조뿐만 아니라, 네트워크 수신 주기와 물리 업데이트 주기 사이의 시각적 보간도 중요하다는 점을 배웠습니다. 단순히 위치 데이터를 동기화하는 것만으로는 충분하지 않고, 원격 클라이언트에서 어떻게 보이는지도 함께 고려해야 한다는 것을 확인했습니다.
